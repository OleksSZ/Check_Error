# oopCheck.py

Статический анализатор Python-кода на базе модуля `ast` (стандартная
библиотека). Ищет нарушения принципов ООП и потенциальные логические баги,
которые обычный запуск скрипта в терминале не покажет (код работает без
ошибок до тех пор, пока не попадёт в нужную ветку).

Работает без сторонних зависимостей — только `python3`.

## Возможности

- Проверка одного файла, нескольких файлов сразу или целой директории
  (рекурсивно обходит структуру проекта/пакетов).
- Итоговый отчёт пишется в `checks.log` (путь настраивается).
- Три категории замечаний: `BUG` (вероятный логический баг), `OOP`
  (нарушение принципов ООП), `STYLE` (стилевые улучшения).
- Отчёт группируется по файлам, отсортирован по важности, в конце — сводка
  по количеству замечаний каждой категории.

## Установка

Файл самодостаточный, ничего ставить не нужно, кроме Python 3.8+.

```bash
python3 --version   # проверить, что 3.8 или новее
```

## Использование

```bash
# один файл
python3 oopCheck.py my_script.py

# несколько файлов сразу
python3 oopCheck.py file1.py file2.py file3.py

# весь проект целиком (рекурсивно найдёт все .py файлы)
python3 oopCheck.py ./my_project/

# можно смешивать файлы и директории в одной команде
python3 oopCheck.py ./my_project/ extra_script.py

# указать своё имя/путь отчёта (по умолчанию — checks.log в текущей папке)
python3 oopCheck.py ./my_project/ --output report.log
python3 oopCheck.py ./my_project/ -o report.log

# дополнительно сохранить отчёт в JSON рядом с .log (то же имя, .json)
python3 oopCheck.py ./my_project/ --json

# настроить порог цикломатической сложности (по умолчанию 10)
python3 oopCheck.py ./my_project/ --max-complexity 6
```

Скрипт также печатает краткую сводку прямо в терминал (сколько файлов
проверено и сколько найдено замечаний), а полный разбор — в файле отчёта.

Директории `__pycache__`, `venv`, `.venv` и скрытые папки (начинаются с `.`)
при обходе проекта пропускаются автоматически.

## Межфайловый анализ (наследование по всему проекту)

При проверке директории скрипт сначала одним проходом собирает реестр всех
классов проекта (имя, файл, родители, методы, `self.*`-атрибуты), а уже
потом, во втором проходе, реально проверяет файлы. Это позволяет:

- видеть атрибуты, унаследованные от родителя из **другого файла**, и не
  ругаться на `ATTR-MISS` там, где атрибут на самом деле задаётся в
  родительском классе;
- ловить `NO-SUPER-INIT` (забытый `super().__init__()`), даже если
  родитель определён в другом модуле проекта.

Если родительский класс — из внешней библиотеки (например,
`unittest.TestCase`) и его исходники не входят в проверяемый проект, обе
проверки для такого класса **не выполняются вообще**, чтобы не выдавать
ложные срабатывания на код, который не виден анализатору.

## Тестовые скрипты для самопроверки

В папке `test_scripts/` лежат файлы, специально написанные с багами и
конструкциями для тестирования конкретных проверок. Полезно после любых
правок `oopCheck.py` — прогнать их и убедиться, что ничего не сломалось.

| Файл | Что демонстрирует | Как запускать |
|---|---|---|
| `1_complexity_game.py` | Цикломатическая сложность: вложенные `if`/`elif` (оружие → враг → доп. условие). Ожидаемый результат: `HIGH-COMPLEXITY`, сложность 8. | `python3 oopCheck.py test_scripts/1_complexity_game.py --max-complexity 5` |
| `2_cross_file_base.py` + `3_cross_file_child.py` | Межфайловый анализ наследования: родительский класс `Animal` в одном файле, наследник `Dog` — в другом, забыт `super().__init__()`. Плюс класс `DogTest(unittest.TestCase)`, который НЕ должен дать ложных срабатываний (родитель вне проекта). Проверяются **обязательно вместе**, отдельно друг без друга не имеют смысла — без пары чекер не увидит, что `Animal` вообще существует. | `python3 oopCheck.py test_scripts/2_cross_file_base.py test_scripts/3_cross_file_child.py` |
| `4_general_bugs_demo.py` | Общий "стресс-тест" — почти все проверки сразу в одном файле (21 замечание): мутабельные default-аргументы, class-level мутабельные атрибуты, `except: pass`, `is` для строк, забытый `return`, `__eq__` без `__hash__` и т.д. | `python3 oopCheck.py test_scripts/4_general_bugs_demo.py` |

Прогнать всё скопом одной командой, с JSON-отчётом в придачу:

```bash
python3 oopCheck.py test_scripts/ --json -o test_run.log
```

P.s Файлы `2_cross_file_base.py` и `3_cross_file_child.py` — это НЕ рабочая
программа, их нельзя запускать напрямую через `python3 3_cross_file_child.py`
(импорт `from base import Animal` не резолвится под такими именами файлов).
Они существуют только для того, чтобы их анализировал `oopCheck.py`.

## Полный список проверок

### BUG — вероятные логические баги

| Код | Что ищет |
|---|---|
| `MUT-DEF` | Изменяемое значение по умолчанию (`def f(x=[])`) — общее состояние между всеми вызовами функции. |
| `ATTR-MISS` | `self.attr` читается методом, но нигде в классе явно не присваивается — риск `AttributeError`. |
| `RET-MIX` | В одних `return` есть значение, в других — нет. Возможен случайный `None`. |
| `CLASS-MUT-ATTR` | Список/словарь/множество объявлены на уровне класса — общий объект на ВСЕ экземпляры сразу, а не отдельный на каждый. |
| `BARE-EXCEPT` | Голый `except:` — перехватывает вообще всё, включая `KeyboardInterrupt`/`SystemExit`. |
| `EXCEPT-PASS` | `except ...: pass` — исключение проглатывается молча, без логирования. |
| `FLOAT-EQ` | Сравнение `float` через `==`/`!=` — ненадёжно из-за погрешностей округления. |
| `INF-LOOP` | `while True` без `break` внутри тела — потенциально бесконечный цикл. |
| `IS-LITERAL` | `is`/`is not` для сравнения с числом или строкой — из-за интернирования в CPython результат непредсказуем. |
| `UNUSED-VAR` | Локальная переменная присваивается, но нигде дальше не читается — забытая логика или опечатка в имени. |
| `HIGH-COMPLEXITY` | Цикломатическая сложность функции выше порога (по умолчанию 10, настраивается через `--max-complexity`) — слишком много независимых путей выполнения. |

### OOP — нарушения принципов ООП

| Код | Что ищет |
|---|---|
| `NAMING` | Имя класса не в `PascalCase` (`CapWords`). |
| `GOD-CLASS` | В классе больше 15 методов — вероятно, нарушен Single Responsibility. |
| `NO-INIT` | Атрибуты создаются вне `__init__` — объект может оказаться в неполном состоянии. |
| `NO-SELF` | Метод не использует `self` — кандидат в `@staticmethod`. |
| `MULTI-INH` | Класс наследуется больше чем от 2 классов сразу — сложный MRO. |
| `NO-SUPER-INIT` | Наследник переопределяет `__init__`, но не вызывает `super().__init__(...)`. |
| `EQ-NO-HASH` | Определён `__eq__` без `__hash__` — объект станет unhashable. |
| `TOO-MANY-ARGS` | Больше 6 параметров у функции/метода (без учёта `self`/`cls`). |

### STYLE — стилевые улучшения

| Код | Что ищет |
|---|---|
| `NONE-EQ` | Сравнение с `None` через `==`/`!=` вместо `is`/`is not`. |
| `SHADOW-BUILTIN` | Имя переменной/функции/класса совпадает со встроенным именем Python (`list`, `id`, `type` и т.д.). |
| `UNUSED-IMPORT` | Импорт нигде в файле не используется. |

## Известные ограничения

Это эвристический анализ AST, а не полноценная система типов — возможны
ложные срабатывания:

- `ATTR-MISS` не видит атрибуты, созданные через `@dataclass`,
  `__slots__`, `setattr()` или унаследованные от родительского класса
  (анализ идёт только внутри одного класса, без учёта иерархии между
  файлами).
- `UNUSED-VAR` не спускается в конструкции с `nonlocal`/замыкания идеально
  и не учитывает переменные, используемые только во вложенных
  функциях/классах (там срабатывает своя, отдельная проверка).
- `NO-SELF` не отличает методы, которые специально не используют `self`,
  но должны остаться обычным методом по семантике интерфейса (например,
  реализация абстрактного метода).
- `ATTR-MISS` и `NO-SUPER-INIT` учитывают наследование между файлами
  проекта (см. раздел "Межфайловый анализ" выше), но **не** резолвят
  реальные Python-импорты — если два класса в разных файлах случайно
  называются одинаково, реестр использует первый найденный и может
  перепутать их. Для внешних (не в проекте) родителей обе проверки
  отключаются, чтобы не шуметь.
- `HIGH-COMPLEXITY` считает количество точек ветвления линейно (плюс 1 за
  `if`/`elif`, `for`, `while`, `except`, каждый `and`/`or`, тернарник,
  условие в comprehension). Это НЕ то же самое, что полное число
  уникальных путей выполнения (которое росло бы перемножением веток и
  могло бы быть огромным) — это оценка "сколько тестов нужно для покрытия
  всех веток", стандартная метрика McCabe.

Если что-то из этого шумит в конкретном проекте — проще всего закомментировать
соответствующую проверку в `oopCheck.py` или отфильтровать код замечания
при чтении `checks.log`.

## Как расширить

Каждая проверка — это отдельный метод в классе `FileChecker`
(`_check_*`), который вызывает `self.add(node, severity, code, message)`.
Чтобы добавить новую проверку:

1. Написать метод `_check_something(self, node)`, использующий `ast`.
2. Вызвать его либо из `visit_FunctionDef`/`visit_ClassDef` (для проверок
   уровня функции/класса), либо из `check_generic_bugs` (для проверок по
   всему дереву через `ast.walk`).
3. Использовать новый уникальный `code` (например, `"MY-CHECK"`).
