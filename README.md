# oopCheck.py

Статичний аналізатор Python-коду на базі модуля `ast` (стандартна
бібліотека). Шукає порушення принципів ООП і потенційні логічні баги,
які звичайний запуск скрипта в терміналі не покаже (код працює без
помилок доти, доки не потрапить у потрібну гілку).

Працює без сторонніх залежностей — лише `python3`.

## Можливості

- Перевірка одного файлу, кількох файлів одразу або цілої директорії
  (рекурсивно обходить структуру проєкту/пакетів).
- Підсумковий звіт записується в `checks.log` (шлях налаштовується).
- Три категорії зауважень: `BUG` (імовірний логічний баг), `OOP`
  (порушення принципів ООП), `STYLE` (стильові покращення).
- Звіт групується за файлами, відсортований за важливістю, наприкінці —
  зведення за кількістю зауважень кожної категорії.

## Встановлення

Файл самодостатній, нічого встановлювати не потрібно, крім Python 3.8+.

```bash
python3 --version   # перевірити, що 3.8 або новіша
```

## Використання

```bash
# один файл
python3 oopCheck.py my_script.py

# кілька файлів одразу
python3 oopCheck.py file1.py file2.py file3.py

# увесь проєкт цілком (рекурсивно знайде всі .py файли)
python3 oopCheck.py ./my_project/

# можна змішувати файли й директорії в одній команді
python3 oopCheck.py ./my_project/ extra_script.py

# вказати своє ім'я/шлях звіту (за замовчуванням — checks.log у поточній папці)
python3 oopCheck.py ./my_project/ --output report.log
python3 oopCheck.py ./my_project/ -o report.log

# додатково зберегти звіт у JSON поруч із .log (те саме ім'я, .json)
python3 oopCheck.py ./my_project/ --json

# налаштувати поріг цикломатичної складності (за замовчуванням 10)
python3 oopCheck.py ./my_project/ --max-complexity 6
```

Скрипт також друкує коротке зведення прямо в термінал (скільки файлів
перевірено і скільки знайдено зауважень), а повний розбір — у файлі звіту.

Директорії `__pycache__`, `venv`, `.venv` і приховані папки (починаються з `.`)
під час обходу проєкту пропускаються автоматично.

## Міжфайловий аналіз (наслідування по всьому проєкту)

Під час перевірки директорії скрипт спочатку одним проходом збирає реєстр усіх
класів проєкту (ім'я, файл, батьківські класи, методи, `self.*`-атрибути), а вже
потім, у другому проході, власне перевіряє файли. Це дає змогу:

- бачити атрибути, успадковані від батьківського класу з **іншого файлу**, і не
  сваритися на `ATTR-MISS` там, де атрибут насправді задається в
  батьківському класі;
- ловити `NO-SUPER-INIT` (забутий `super().__init__()`), навіть якщо
  батьківський клас визначено в іншому модулі проєкту.

Якщо батьківський клас — із зовнішньої бібліотеки (наприклад,
`unittest.TestCase`) і його вихідний код не входить до проєкту, що перевіряється,
обидві перевірки для такого класу **не виконуються взагалі**, щоб не видавати
хибних спрацювань на код, якого аналізатор не бачить.

## Тестові скрипти для самоперевірки

У папці `Error_Scripts/` лежать файли, спеціально написані з багами та
конструкціями для тестування конкретних перевірок. Корисно після будь-яких
правок `oopCheck.py` — прогнати їх і переконатися, що нічого не зламалося.

| Файл | Що демонструє | Як запускати |
|---|---|---|
| `1_complexity_game.py` | Цикломатична складність: вкладені `if`/`elif` (зброя → ворог → додаткова умова). Очікуваний результат: `HIGH-COMPLEXITY`, складність 8. Без `--max-complexity 5` зауваження не буде (8 менше за поріг 10 за замовчуванням). | `python3 oopCheck.py Error_Scripts/1_complexity_game.py --max-complexity 5` |
| `2_cross_file_base.py` + `3_cross_file_child.py` | Міжфайловий аналіз наслідування: батьківський клас `Animal` в одному файлі, нащадок `Dog` — в іншому, забуто `super().__init__()`. Плюс клас `DogTest(unittest.TestCase)`, який НЕ має давати хибних спрацювань (батьківський клас поза проєктом). Перевіряються **обов'язково разом**, окремо один без одного не мають сенсу — без пари чекер не побачить, що `Animal` взагалі існує. У самому `2_cross_file_base.py` помилок навмисно немає. | `python3 oopCheck.py Error_Scripts/2_cross_file_base.py Error_Scripts/3_cross_file_child.py` |
| `4_general_bugs_demo.py` | Загальний "стрес-тест" — майже всі перевірки одразу в одному файлі (21 зауваження): змінювані default-аргументи, змінювані атрибути рівня класу, `except: pass`, `is` для рядків, забутий `return`, `__eq__` без `__hash__` тощо. | `python3 oopCheck.py Error_Scripts/4_general_bugs_demo.py` |

Прогнати все гуртом однією командою, з JSON-звітом на додачу:

```bash
python3 oopCheck.py Error_Scripts/ --json -o test_run.log
```

P.S. Файли `2_cross_file_base.py` і `3_cross_file_child.py` — це НЕ робоча
програма, їх не можна запускати напряму через `python3 3_cross_file_child.py`
(імпорт `from base import Animal` не резолвиться під такими іменами файлів).
Вони існують лише для того, щоб їх аналізував `oopCheck.py`.

## Повний список перевірок

### BUG — імовірні логічні баги

| Код | Що шукає |
|---|---|
| `MUT-DEF` | Змінюване значення за замовчуванням (`def f(x=[])`) — спільний стан між усіма викликами функції. |
| `ATTR-MISS` | `self.attr` читається методом, але ніде в класі явно не присвоюється — ризик `AttributeError`. |
| `RET-MIX` | В одних `return` є значення, в інших — немає. Можливий випадковий `None`. |
| `CLASS-MUT-ATTR` | Список/словник/множину оголошено на рівні класу — спільний об'єкт на ВСІ екземпляри одразу, а не окремий для кожного. |
| `BARE-EXCEPT` | Голий `except:` — перехоплює взагалі все, зокрема `KeyboardInterrupt`/`SystemExit`. |
| `EXCEPT-PASS` | `except ...: pass` — виняток ковтається мовчки, без логування. |
| `FLOAT-EQ` | Порівняння `float` через `==`/`!=` — ненадійне через похибки округлення. |
| `INF-LOOP` | `while True` без `break` усередині тіла — потенційно нескінченний цикл. |
| `IS-LITERAL` | `is`/`is not` для порівняння з числом або рядком — через інтернування в CPython результат непередбачуваний. |
| `UNUSED-VAR` | Локальній змінній присвоюється значення, але далі вона ніде не читається — забута логіка або друкарська помилка в імені. |
| `HIGH-COMPLEXITY` | Цикломатична складність функції вища за поріг (за замовчуванням 10, налаштовується через `--max-complexity`) — забагато незалежних шляхів виконання. |

### OOP — порушення принципів ООП

| Код | Що шукає |
|---|---|
| `NAMING` | Ім'я класу не в `PascalCase` (`CapWords`). |
| `GOD-CLASS` | У класі більше 15 методів — імовірно, порушено Single Responsibility. |
| `NO-INIT` | Атрибути створюються поза `__init__` — об'єкт може опинитися в неповному стані. |
| `NO-SELF` | Метод не використовує `self` — кандидат у `@staticmethod`. |
| `MULTI-INH` | Клас успадковується більше ніж від 2 класів одразу — складний MRO. |
| `NO-SUPER-INIT` | Нащадок перевизначає `__init__`, але не викликає `super().__init__(...)`. |
| `EQ-NO-HASH` | Визначено `__eq__` без `__hash__` — об'єкт стане unhashable. |
| `TOO-MANY-ARGS` | Більше 6 параметрів у функції/методу (без урахування `self`/`cls`). |

### STYLE — стильові покращення

| Код | Що шукає |
|---|---|
| `NONE-EQ` | Порівняння з `None` через `==`/`!=` замість `is`/`is not`. |
| `SHADOW-BUILTIN` | Ім'я змінної/функції/класу збігається з вбудованим ім'ям Python (`list`, `id`, `type` тощо). |
| `UNUSED-IMPORT` | Імпорт ніде у файлі не використовується. |

## Відомі обмеження

Це евристичний аналіз AST, а не повноцінна система типів — можливі
хибні спрацювання:

- `ATTR-MISS` не бачить атрибутів, створених через `@dataclass`,
  `__slots__`, `setattr()` або оголошених на рівні класу.
- `UNUSED-VAR` не ідеально спускається в конструкції з `nonlocal`/замиканнями
  і не враховує змінних, що використовуються лише у вкладених
  функціях/класах (там спрацьовує своя, окрема перевірка).
- `NO-SELF` не відрізняє методів, які спеціально не використовують `self`,
  але за семантикою інтерфейсу мають залишитися звичайним методом (наприклад,
  реалізація абстрактного методу).
- `ATTR-MISS` і `NO-SUPER-INIT` враховують наслідування між файлами
  проєкту (див. розділ "Міжфайловий аналіз" вище), але **не** резолвять
  справжні Python-імпорти — якщо два класи в різних файлах випадково
  мають однакові імена, реєстр використовує перший знайдений і може
  їх переплутати. Для зовнішніх (не з проєкту) батьківських класів обидві перевірки
  вимикаються, щоб не шуміти.
- `HIGH-COMPLEXITY` рахує кількість точок розгалуження лінійно (плюс 1 за
  `if`/`elif`, `for`, `while`, `except`, кожен `and`/`or`, тернарний оператор,
  умову в comprehension). Це НЕ те саме, що повна кількість
  унікальних шляхів виконання (яка зростала б множенням гілок і
  могла б бути величезною) — це оцінка "скільки тестів потрібно для покриття
  всіх гілок", стандартна метрика McCabe.

Якщо щось із цього шумить у конкретному проєкті — найпростіше закоментувати
відповідну перевірку в `oopCheck.py` або відфільтрувати код зауваження
під час читання `checks.log`.

## Як розширити

Кожна перевірка — це окремий метод у класі `FileChecker`
(`_check_*`), який викликає `self.add(node, severity, code, message)`.
Щоб додати нову перевірку:

1. Написати метод `_check_something(self, node)`, що використовує `ast`.
2. Викликати його або з `visit_FunctionDef`/`visit_ClassDef` (для перевірок
   рівня функції/класу), або з `check_generic_bugs` (для перевірок по
   всьому дереву через `ast.walk`).
3. Використати новий унікальний `code` (наприклад, `"MY-CHECK"`).
